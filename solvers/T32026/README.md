# T3 2026 Solver Notes

T3 is selectable in the portal; official term dates remain TBD. GA1 is the September 2026 exam bundle.

## GA1: Developer Tools

- Official source snapshot: `ga1/exam-source.js` from `https://exam.sanand.workers.dev/exam-tds-2026-09-ga1.js`.
- The ordered registry exposes all 16 official question IDs and keeps their original order.
- Exact local generation is implemented where the bundle's answer is reproducible without a live user environment: Q3 grader-compatible HTTPie response, Q4 Prettier hash, Q5 valid JSON source, Q7 reorganization hash, Q8 revenue, and Q11 cosine rankings.
- Q6, Q14 and Q15 are wired to the separate T3 GA1 API (`tds-roe-solver-api/T32026/GA1`, hosted at `tds-roe-solver-api-t12026.onrender.com`; integration contract in that folder's `SOLVER_INTEGRATION_GUIDE.md`). Q6 answers `/ga1/{email}/effective-config` and Q14 answers `/ga1/{email}/mcp`, built from the trimmed, lower-cased, URL-encoded email by `ga1/api-client.js`. Q15 cannot be precomputed: its form takes the student's private Ledger link, validates it (exam host, `q-ledger-agent-server`, same email, has `quizSign`) before anything is sent, wakes the Render API via `/health`, posts the link once to `/ga1/onboard`, verifies that the returned submit URL points back at this API for this email, and then fills the real Answer box through `window.tdsPatchAnswer` (see `app.js`). Live-checked against the official grader logic: Q6 matched the exam bundle's own config generator for 5 emails x 4 override sets, and Q14 passed the full MCP handshake plus five fresh-challenge calls.
- Q1 returns the fixed T2 GA1-compatible three-line answer for every user; it is a shared constant, not machine-detected output. Q9 includes a personalized, ready-to-publish page and a beginner deployment/troubleshooting guide, but each learner must publish and submit their own GitHub Pages URL. Q10 can be solved directly from an uploaded or pasted copy of the student's `history.fi`: `ga1/git-history.js` parses the `git fast-import` stream locally (byte-counted and delimited `data`, marks, inline blobs, quoted paths, `from`/`merge`, `R`/`C`/`D`/`deleteall`), rebuilds the tree after every commit, and reports the commit that first introduced each `stg_` token plus whether it was rotated out; an ambiguous history is shown as candidates, not as a solved answer. The beginner Git walkthrough remains as the manual cross-check. Q2 is relayed through the live API (see below) because the exam server sends no `Access-Control-Allow-Origin`, so a page on another origin cannot read `questionData`, let alone the `X-Exam-Code` header. Other guide questions require authenticated data, live LLM calls, signed recording/game artifacts, or the separate API project.
- T2 GA1 parity tests protect shared Q5 JSON and Q7 file-reorganization algorithms for lowercase emails. T3's case-sensitive seeds remain authoritative; do not import T2's email normalization into T3.

## Architecture

- `ga1/registry.js`: official question order and API metadata.
- `ga1/api-client.js`: live API origin, email normalisation and URL building shared by Q6/Q14 (and Q15's origin).
- `ga1/q12-llm-yes-no.js`: Q12 ships only prompts that passed every live run against the real exam models (`gpt-5.6-luna` must say Yes, `gpt-5.4-mini` must say No; case-sensitive whole words, 100 characters max, same prompt to both, no system prompt). Live testing on 2026-10-13 showed that name/identity prompts do not work (neither model knows the name `gpt-5.6-luna`; a mini-keyword prompt passed only ~3 runs in 4), while exact arithmetic does: luna multiplies four-digit numbers exactly and mini is off by 0.01-0.2%. So every prompt states a true fact about products (digit sums, or sums of products). Each `CANDIDATES` entry records `tested` as runs passed/runs; `check.mjs` refuses any entry that is not a perfect record of at least 8 runs. The same file contains the in-browser tester (student's own aipipe.org token in a password field, sent only to aipipe.org, never stored) that re-ranks the prompts plus a custom one and fills the Answer box via `window.tdsPatchAnswer`. LLM behaviour can drift, so re-test with the tester before submitting.
- **Q16 (`ga1/q16-tangram.js`)** — the exam's 100 silhouettes each have a stored, verified arrangement (`ga1/tangram-solutions.js`: seven `[x, y, orientation, reflected]` poses in inventory order, 1/16-unit coordinates). `ga1/tangram-geometry.js` is an unchanged copy of the game's own exact geometry (`algebraic.js` + `adapter.js` + the match-key part of `kernel.js` from tds-network-games.sanand.workers.dev), so every arrangement is checked against the exam's expected match key offline: `check.mjs` verifies all stored entries, rejects shifted or foreign arrangements, and `solve()` re-verifies before showing anything. The exam picks the silhouette with `seedrandom(email + '#q-visual-game-tangram')` (exact email); the module does the same. In a real browser `solve()` calls the game's `/api/visual/attest` (CORS is open, an empty `client_report` is accepted), re-checks `invalid === false`, `match_key === expected` and the JWT `sub`, and returns the signed token as a `solved` answer (cached per email; the exam's token check has no expiry). Node and any failure fall back to a guide with the diagram, a placement table, a pre-assembled board link (`#v=1&s=<base64url poses>`, the game's own state-link format) and a button that retries signing and fills the Answer box through `window.tdsPatchAnswer`. Never call the game server from tests: the browser path is gated on a `Mozilla/` user agent. Provenance: all 100 stored arrangements come from the open-source HypeMonk/tangram-solver project (its "Complete Tangram coverage with all 100 verified arrangements" update) and are re-verified here against the exam's expected match keys; `check.mjs` requires exactly 100 verified entries and fails if any stops verifying. The module still falls back to the manual guide for a silhouette with no stored arrangement, in case the exam ever adds one.
- **Q2 (`ga1/q02-http-headers.js`)** — the exam server sends no CORS headers, so a page on another origin cannot read the signed `questionData` response itself; the separate API can. The form takes the student's private Q2 link (the URL inside the `curl -i` command), validates it in the browser before anything is sent (exam host only, `/questionData`, a valid `q-…` question id, a `quizSign`, same email as the workspace), wakes the Render API via `/health` (reusing `waitForApi` from the Q15 module), then POSTs `{question_data_url}` once to `{ORIGIN}/ga1/{email}/answers/headers` and reads `answer_text`. The reply is only trusted if the code looks like one token and any echoed `email` matches; every documented API error (400/409/422/429/502 `UPSTREAM_REJECTED` with 401/403 = expired signature/504) maps to a specific, link-free message. On success the Answer box is filled through `window.tdsPatchAnswer` and the link box is cleared. The code rotates hourly, so the result says when it was fetched. The manual `curl -i` steps stay in the guide as the no-API fallback. **Automatic fill:** in a real browser (a `Mozilla/` user agent; never Node) `solve()` also starts a background `autoFetchStored()` — wake the API, `POST {}` with no link (the API then uses the signature it stored when the email was onboarded through Q15, else answers 409 and the form stays) — and patches the Answer box as soon as the workspace has registered the question (retrying for about a minute). It runs once per email per page load, and Q15 re-triggers it through `window._t3ga1q2AutoFetch` right after a successful onboarding, so one pasted link (in Q2 or Q15) fills both. The API's stored signature lives in its SQLite file, so after a Render restart the form is needed again. The same API also offers Q10 (`/answers/git-forensics`) and Q11 (`/answers/cosine`) routes; only Q2 is wired so far (Q10 has the local finder, Q11 is computed locally).
- **Q9 / Q13 console helper (`console/t3-ga1-helper.js`, guide section in `ga1/console-helper-guide.js`)** — a script the student pastes into the browser console on their own logged-in exam page (`https://exam.sanand.workers.dev/tds-2026-09-ga1`). It reads the email and signed link from `localStorage.user` and exposes `window.t3ga1`: `q9.page()/commands()/check(url)` and `q13.commands()/check(url)`. `q9.commands()` prints git + `gh` commands to publish the ready-made page; `q9.check(url)` downloads the live page and fills `#q-github-pages` only if the email is really inside `<!--email_off-->` markers. `q13.commands()` prints the full local termlog workflow (login, rec, the student's own challenge link, all six real ROT13/hex/reverse pipelines, verify, pack, upload); `q13.check(url)` checks the archive is a gzip download when the host allows it (otherwise fills it and says it could not verify). The portal's Q9 and Q13 guides embed a Copy button that fetches the helper from the portal. `check.mjs` runs the helper in a `vm` sandbox with a fake exam page, covering the guard rails, command content, shell/HTML escaping, every pass/fail path and the fact that it makes no request except the URL being checked, plus mutation checks. Deliberately NOT ported from the avirenusurya/tds-solver-backend reference: its fetch patches that fabricate grader responses (fake `/effective-config`, fake GitHub-Pages proxy page, fake AI Pipe that always says luna=Yes), and its server-side termlog flow that takes the student's Google `auth.json`/callback — handing a login to a third party and producing the proof-of-work for the student. The helper only prints commands for the student's own terminal and verifies what they actually published.
- `ga1/git-history.js`: pure fast-import parser and token analysis used by Q10 (no DOM, runs under Node in `check.mjs`).
- `ga1/runtime.js`: shared response normalization, diagnostics, and failure containment.
- `ga1/utils.js`: exact-vs-normalized email handling, local seeded RNG access, SHA-256, safe dynamic Markdown fences, and guide result helper.
- `ga1/generators.js`: deterministic generation/reconstruction routines.
- `ga1/qNN-*.js`: question-specific solver or guide modules.
- `ga1/exam-source.js`: pinned official bundle snapshot used for audits; do not load it in the application.
- `../../vendor/seedrandom.min.js`: pinned local `seedrandom@3.0.5`; the seeded answers do not depend on a third-party RNG CDN. Q4's pinned Prettier CDN load has a 12-second timeout and degrades to actionable instructions if unavailable.

Run `node check.mjs --t3-ga1-only` for focused contract/seed checks, or `node check.mjs --t3-ga1-scale` to exercise all 16 questions across 1,000 distinct email seeds. `npm run check` includes the GA1 focused checks with the existing project suite.

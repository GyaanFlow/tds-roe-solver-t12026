## 1 · TL;DR (30-second read)

An automated tool flagged Swiss packet **CH-2025-000522** because the declared tariff code **`90211000`** doesn't match **Helios `90211090`**. Should you escalate it as a *likely declaration error*?

The honest read: **No — do not escalate.** The declared `90211000` is **exactly the code the country tariff matrix approves for P1001 in Switzerland** (Swiss local nomenclature, effective on the entry date). The `90211090` in the flag is the **Helios commercial commodity code** — an eight-digit value the master file itself labels *"migration-mapped"* and *"not customs-ruling status"*, and it happens to equal the **EU CN8** code, a *different* nomenclature. At the internationally harmonised **six-digit** level both are `902110` — **no mismatch at all**; they differ only in the national tail digits, which are jurisdiction-specific *by design*.

**Defensible decision → *Do not escalate as a declaration error; treat it as a cross-code-system false positive and fix the comparator.*** This scores because it is **evidence-based**, **calibrated** (you're not "clearing" it forever — you name the Tares/ruling confirmation that would make it legally final), and it **resists the naive string-compare trap** the exam is built around.

## 2 · Scenario in plain English

Asterion Ortho's EMEA customs team runs an **automated comparison** that cross-checks each declared tariff code against a reference value. On packet **CH-2025-000522** it fired a **mismatch** flag: the broker declared **`90211000`**, but the tool expected **Helios `90211090`**. Your job: decide whether this is a **likely declaration error worth escalating**, or something else — using only the packet + the reference data provided.

Why it matters: this is a **calibration test dressed up as a data check.** Two eight-digit strings differ, so a naive tool screams "error." But customs codes live in **different nomenclatures per jurisdiction** (Switzerland runs its own tariff; the EU runs CN8), they carry **effective dates** and **versions**, and a **commercial master file is not a customs ruling.** Escalating a cross-system difference as a "declaration error" wastes the broker's time, erodes trust in the flagging tool, and misreads the evidence. The skill is spotting that the declaration actually **matches the jurisdiction-correct authority**, and that the tool is comparing apples (Swiss code) to oranges (EU/Helios code).

## 5 · Verified data findings (the frozen analysis — cite these)

**1. The declared code matches the Swiss authority exactly.**
`country_tariff_matrix.xlsx` → **Swiss Matrix** lists P1001 (Switzerland) as **Approved CN8 `90211000`**, effective 2025-01-01 with no end date — i.e. **current on the 2025-11-04 entry date**. The declaration's `90211000` is therefore the **jurisdiction-correct** code, not an error. *(source: country_tariff_matrix.xlsx, Swiss Matrix; declaration.pdf)*

**2. The flag's benchmark is a commercial code, not a customs ruling.**
The `90211090` in `review_note.txt` is P1001's **Helios Commodity Code** from `product_master_current.xlsx`. Its own **Read Me** says the Helios code is an *"Eight-character current value. Migration mappings were used where a local approved code was not supplied,"* and record status is *"Commercial master-data status, **not customs-ruling status**."* So the tool is checking against a **commercial** reference, not a Swiss classification authority. *(source: product_master_current.xlsx, Read Me)*

**3. The two codes belong to different nomenclatures.**
Helios `90211090` is **identical to the EU CN8** for P1001 (EU Matrix, current from 2025-07-01). The tariff matrix Read Me states plainly: *"EU entries use CN8; **Switzerland uses a Swiss local tariff code. Matching strings across jurisdictions is not expected.**"* Comparing a Swiss code to an EU/Helios code is an **apples-to-oranges** comparison. *(source: country_tariff_matrix.xlsx, EU Matrix + Read Me)*

**4. At the harmonised six-digit level there is *no* mismatch.**
`90211000`, `90211090` (EU/Helios current) and `90211010` (EU pre-July) all share **HS6 `902110`** — the internationally-harmonised subheading for orthopaedic appliances. The divergence is only in the **national 7th–8th digits**, which every jurisdiction sets differently. So the goods are classified the *same* at the level that is actually harmonised. *(source: both reference files; P1001 Base HS6 = 902110)*

**5. There's even a version/effective-date trap baked into the reference.**
The EU code for P1001 itself **changed** `90211010 → 90211090` at **2025-07-01**. So `90211090` is merely the *current* EU value; a comparator that ignores **effective dates** would mis-flag pre-July entries too. This is direct evidence that "one true code" is a fiction here. *(source: country_tariff_matrix.xlsx, EU Matrix)*

**6. The comparator is structurally blind to all of the above.**
`canonical-schema-v0.3.md` lists as **"Not yet modeled": code-system identifier, nomenclature version, effective dates, …** Without those fields, an automated **string** compare **cannot distinguish** a genuine misclassification from a cross-nomenclature difference. The mismatch flag is an **artifact of that schema gap.** *(source: canonical-schema-v0.3.md)*

**7. Nothing is at stake on duty, and there's no origin problem.**
The declaration shows **duty 0.0% / CHF 0.00** with **no preference claimed**; origin **US** is consistent across declaration, invoice and master. (The tariff matrix carries **no duty column**, so treat the *rate* as declaration-sourced, not independently reconfirmed — but both candidate codes sit inside the same HS6, so a duty delta is implausible.) *(source: declaration.pdf; commercial_invoice.pdf; product_master_current.xlsx)*

**8. A separate — and bigger — anomaly the code flag never looked at: the invoice quantity/value doesn't add up.**
The commercial invoice lists **Quantity 10** but **Line value = Unit value = CHF 126,900** — i.e. **Line ≠ Qty × Unit.** If the quantity is right, the line is understated ~10× (10 × 126,900 = **CHF 1,269,000**, a **CHF 1,142,100** gap), and the **declared customs value follows the lower CHF 126,900 line figure.** The air waybill muddies it further — only **4 pieces**, matching neither 10 nor 1. So three packet documents imply **three different quantities (10 / 1 / 4).** This is an **internal-consistency / valuation** question that is *independent of the tariff-code flag* — and potentially far more material than a duty-neutral code cosmetic. **Calibration:** flag it and ask for the true quantity + unit basis; it is **not** proof of undervaluation on its own (could be a unit-vs-line labelling quirk or a quantity typo), and it does **not** change the *code* decision. *(source: commercial_invoice.pdf; air_waybill.pdf; declaration.pdf)*

| The flag implies | What the data actually shows | Verdict |

| "90211000 ≠ 90211090 → declaration error" | 90211000 **is** the approved **Swiss** code for P1001; 90211090 is the **EU/Helios** code | **Different systems, not an error** |
| "Helios is the code it *should* be" | Helios = commercial master data, migration-mapped, *"not customs-ruling status"* | **Wrong authority to compare against** |
| "The codes are genuinely different goods" | Both are **HS6 902110**; differ only in national tail digits | **Same classification where it's harmonised** |
| "The tool caught a real problem" | Schema models **no** code-system / version / effective date | **False positive from a schema gap** |
| "This needs escalating today" | Duty 0%, no preference, US origin consistent | **No stake; no error to escalate** |

## 7 · Traps that lose marks here

> [!CAUTION]
> - **Trusting the string compare.** Two different eight-digit strings is the *whole* trap. `90211000` (Swiss) vs `90211090` (EU/Helios) differ because the **nomenclatures** differ, not because the broker erred.
> - **Treating Helios as the source of truth.** The master file explicitly says it is **commercial** data, migration-mapped, **not a customs ruling.** Don't let "current value" fool you.
> - **Ignoring HS6.** If you normalise to six digits (`902110`) the mismatch vanishes — say so; it's the cleanest single piece of evidence.
> - **Forgetting effective dates.** The EU code itself changed in July 2025. "The right code" is date- *and* jurisdiction-dependent.
> - **Over-committing.** Don't declare it *permanently* fine either — the Swiss Matrix says *"confirm Tares/ruling for legal use."* Calibrate: *not an error to escalate*, **and** name the confirmation that would make it legally final.
> - **Escalating a duty-neutral, no-preference line** as if revenue were at risk. It isn't.
> - **Tunnel-visioning on the code and missing the real anomaly.** The tariff mismatch is a false positive — but the same invoice shows **Qty 10 with a 1-unit line value** (and the AWB says 4 pcs). *That* quantity/valuation inconsistency (a potential CHF 1.14M gap) is the packet's more material issue, and the code-flag tool never looked at it. (Flag it as a separate item — it doesn't change the *code* call.)

### 8b · Hypotheses to reject (pick 2–3)

- **"`90211000` is a keying error and should be `90211090`."** → **Rejected:** `90211000` is the *jurisdiction-correct* Swiss code; the difference is cross-system, not a dropped/wrong digit.
- **"Helios is the source of truth, so the declaration must conform."** → **Rejected:** Helios is commercial master data, migration-mapped, *"not customs-ruling status."* The Swiss working classification is the right reference — and it says `90211000`.
- **"A mismatch flag means a declaration error."** → **Rejected:** with code-system and version *unmodeled*, a string difference ≠ a misclassification.

### 8c · Missing evidence (name 2–3)

- **Code-system identifier + nomenclature version** stamped on each code (which is Swiss Tares, which is EU CN, which is Helios-internal).
- **The effective-dated Swiss Tares entry / binding ruling** for P1001 (both the Swiss Matrix and its Read Me say *"confirm Tares/ruling for legal use"*).
- **An authoritative duty table** to independently confirm the 0% on the Swiss line (the matrix has no duty column).
- **The true line quantity and unit/line-value basis** for P1001 — the invoice shows Qty 10 but a 1-unit line value (CHF 126,900) and the AWB shows 4 pcs; confirm whether the customs value should be CHF 126,900 or ~CHF 1.27M (separate from the code flag).

### 8e · Safe next action (cheap, correct)

- **Do not** raise it to the broker/importer as a declaration error.
- **Fix the comparison:** compare like-for-like within one nomenclature, or **normalise to HS6** before flagging, and make the tool **code-system- and effective-date-aware**.
- **If legal certainty is needed,** confirm P1001's Swiss classification via **Tares / a binding ruling**, then **close the flag as a cross-nomenclature artifact** with that note. No duty at stake.
